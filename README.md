#  Gazebo Swarm — Drone Communication, Leader Election & Formation Flight

Drone swarm communication, leader election, and formation flight, built on Gazebo Sim + PX4 SITL (the simulator recommended for this internship, after an initial Webots prototype — see the report). Three simulated drones detect each other, notice when one drops off (either by process failure or by going out of radio range), elect a new leader automatically, and now actually fly: the leader loiters a scripted path, the two followers hold a triangle formation on it, and a separation rule keeps every pair at least 1m apart at all times — including through a leader failover mid-flight.

Full write-up: [`RAPPORT_EN.md`](./RAPPORT_EN.md) — the research process, the problems hit along the way and how they got fixed.

The active implementation is the ROS 2 port under [`ros2_ws/`](./ros2_ws) (`swarm_comm` / `swarm_msgs` packages). This root-level `swarm_node.cpp` / `run_swarm.sh` / `worlds/` are the original non-ROS prototype that validated PX4 SITL + MAVSDK on this machine; `ros2_ws` now builds on top of that same PX4/Gazebo setup.

## Where things stand

1. ✅ **Protocol research.** Compared raw Gazebo Transport, ROS 2 and PX4 SITL + MAVLink/MAVSDK as ways to get the drones talking. Went with PX4 SITL + MAVSDK since PX4-Autopilot was already on the machine and it's closer to how a real fleet would be set up.
2. ✅ **Environment setup.** Got PX4 SITL building for the modern `gz-sim` target — had to work around a broken Homebrew Python and an OpenCV version mismatch on an unrelated plugin.
3. ✅ **Communication + leader election.** Timeout-based disconnection detection and sticky majority-vote leader election, tested end to end including the split-brain fix below. Now lives in `ros2_ws/src/swarm_comm/src/swarm_node.cpp`, ported from the original UDP-mesh version at the repo root.
4. ✅ **Persistent Gazebo world.** Drones used to be spawned dynamically and vanished on a simulation reset. Now they live in the world file itself (`worlds/swarm_persistent.sdf`).
5. ✅ **Range-based disconnection + split-brain fix.** Added a simulated 6m radio range so you can disconnect a drone by moving it instead of killing its process. That surfaced a real bug — an isolated drone would elect itself leader and never give it back — which is now fixed.
6. ✅ **ROS 2 port.** Same comm/election logic, rebuilt on ROS 2 Jazzy topics/timers instead of hand-rolled UDP sockets and threads.
7. ✅ **Real PX4 flight.** `swarm_node` now connects to its own PX4 SITL instance over MAVSDK (Telemetry + Action + Offboard), arms, takes off, and flies real Offboard velocity setpoints — no more fake position parameters. Confirms the actual PX4 flight mode after starting Offboard and retries if it silently reverted (see "What's left" — this turned out to be common, not rare).
8. ✅ **Triangle formation.** The elected leader flies a scripted circular loiter (time-keyed, so a new leader picks the path up from wherever it currently is, not from a jump). Both followers hold a fixed triangle offset on the leader's *live* position and heading, with velocity feedforward so they can actually keep pace with a moving leader instead of endlessly tail-chasing it.
9. ✅ **Collision avoidance.** A reactive separation rule keeps every pair of drones ≥ 1m apart, layered on top of the formation-seeking velocity. Validated by forcing close encounters during takeoff and watching the swarm push apart and re-converge with zero persistent oscillation.
10. ✅ **Leader failover in flight.** Killing the current leader mid-flight triggers the existing election unchanged; the new leader re-anchors the loiter path to its own live position and the remaining follower's formation target updates automatically — validated live, not just on the ground.
11. ✅ **Safety guardrails.** A geofence/altitude clamp on every flight target, plus hard altitude *and* horizontal-distance emergency-land backstops checked against actual position (independent of the target clamp — a target-only clamp doesn't stop a drone that's already outside the fence from continuing outward), and an automatic land if Offboard setpoints get rejected repeatedly.
12. ✅ **Straight-line leader path.** The formation logic never assumed a circle — it follows whatever the leader is actually doing. Added a second scripted path (`flight_pattern:=line`, back-and-forth along the east axis) alongside the loiter, selectable per launch, with the same re-anchor-on-taking-leadership behavior as the loiter. Validated in flight: the leader tracks the reference to within centimeters, and both followers hold formation on it.
13. ✅ **Real vs. believed connectivity in the dashboard.** `SwarmStatus` now carries each drone's own per-peer `connected` belief (the same message-timeout state the election uses), shown in `swarm_dashboard.py` next to the live geometric range — the two can disagree (a peer in range but still disconnected for another reason is flagged explicitly), which plain distance alone couldn't show.
14. ✅ **Followers feedforward off the leader's analytical reference velocity, not its telemetry.** `SwarmStatus` carries a separate `ref_vx/ref_vy` — the exact scripted-path velocity the leader is trying to fly — broadcast only by whoever currently believes itself leader. Followers use that instead of the leader's real (noisier, laggier) MAVSDK-derived velocity for both heading estimation and feedforward. Didn't show a dramatic effect on its own in the 6-flight measurement below, but is a strictly better signal to feed forward from and introduced no regression.

## What's left

- **`line`'s instant velocity reversal was one real cause, fixed — but not the whole story.** The original triangle-wave path reversed the leader's velocity *instantly* at each end (a step discontinuity), which snapped a follower's heading-based formation offset to the opposite side in one control tick — a live test caught a follower isolated during exactly this kind of transient fly to 41m from origin. `line_reference()` is now sinusoidal (continuous position *and* velocity everywhere, same idea as the loiter's sin/cos) — the immediate follower Y-wobble did drop from ~6m to ~1-2m. But digging into a *second* live test after that fix, the leader itself later hit the hard geofence at 40.2m and force-landed: the sinusoid's slower cruise near each end of the line meant `leader_speed > 0.2` (the threshold for trusting a velocity sample enough to update heading) was now false for a real fraction of every cycle instead of a literal instant, freezing a follower's heading estimate for seconds at a time near every turnaround. Lowered to `0.03`.
- **Root-caused part of the connectivity fragility: Gazebo's GUI client competing for CPU/GPU with the 3 physics instances.** PX4's gz-sim init script (`px4-rc.gzsim`) spawns a separate `gz sim -g` rendering process by default alongside the headless `-s` server, unless `HEADLESS=1` is set before launching — nothing in this project's own scripts had ever set it. 3 GUI-mode flights logged 4, 4, and 8 `Signal lost` events each (mean 5.3); 3 headless flights of matched duration logged 0, 0, and 4 (mean 1.3) — a real reduction, though not elimination (the third headless run still hit the hard geofence once). `SEPARATION`-floor-violation counts didn't show the same improvement (196, 179, 58 headless vs. 187/102/233 GUI) — that jitter looks like a separate mechanism (formation/control-loop dynamics) than the one driving disconnects (DDS/discovery timing sensitive to system load). Recommendation: use `HEADLESS=1 ./run_swarm.sh` for any automated testing or measurement; keep the GUI for interactive demos where you actually want to watch it fly.
- **The collision-avoidance rule was reworked (anticipatory margin + priority blend + reanchor deadband), then measured properly over 6 flights — and the honest result is a real, still-open problem, not a fix.** The original repulsion only activated exactly at the 1m floor (purely reactive, one control tick from a violation on any real closing speed) and was added to the formation-seeking velocity before a final speed clamp, which could dilute its direction right when a peer was closest. Reworked to (1) start ramping at 1.4m — anticipatory, picked to sit below the formation's own ~1.8-2.0m normal spacing so it doesn't fight steady-state flight — with a quadratic rather than linear ramp, and (2) a priority blend that hands repulsion progressively more of the speed budget as it strengthens instead of a plain vector sum. Also found and fixed a deadband issue where an unplanned leader handoff moments after a near-miss fed a repulsion-polluted velocity sign into the line-reanchor's direction check.
  An earlier 3-flight comparison (198 → 102 → 233 SEPARATION events) was inconclusive on its own — too small a sample. **Redone properly with 6 flights** (headless, with the analytical-feedforward change below applied): SEPARATION-floor-violation counts were 145, 141, 81, 140, 129, 141 (mean 129.5, std. dev. ≈22) — a real, if modest, improvement over the earlier estimates. But **the hard geofence backstop fired in 3 of the 6 flights** (drone reaching 40m+ from origin and force-landing) — a materially *worse* rate than the 3 headless-only flights before this rework (0 of 3). Zero crashes across all 6, and the geofence always caught it safely, but this is the honest headline: whatever causes a drone to accumulate 40m+ of drift is not rare (roughly every other flight) and is not solved by any of the changes made this session. The likely mechanism, traced in one flight: a persistently-close peer (min separation logged down to 0.20-0.23m at times) keeps the priority-blended repulsion chronically active, and a sustained bias in one direction over 100+ seconds is enough to accumulate a large drift even without any single dramatic event. A real fix would need to detect *chronic* (not just instantaneous) proximity and treat it differently — not yet done.
- **Radio range widened 6m → 10m** after live testing showed the triangle formation's own footprint (~1.8-2m) left too little slack — a transient (a hard turn, a moment of separation-avoidance) could push a pair briefly past range for no real reason. More margin, fewer avoidable reconnect cycles; occasional brief excursions still happen since this doesn't touch the underlying cause below.
- **Failover can stall if it lands on a bad connectivity moment — left as is, deliberately.** If the leader disappears at the exact moment the 2 remaining drones are *also* out of range of each other, neither can hold a quorum to elect a new leader (`if (alive.size() == 1) return;`), so both sit frozen on the dead leader's last known position until they reconnect with each other. This looks fixable by letting an isolated drone elect itself after a grace period, but that's exactly the split-brain bug the guard was added to prevent (see item 5 above) — safe-but-not-prompt is the intended trade-off here, not a bug to close.
- **PX4 can silently kick itself back out of Offboard immediately after entering it** (seen live: `Takeoff` → `Offboard` → `Hold` inside a second, no error from MAVSDK — `Offboard::start()` returning success only means PX4 acked the mode-switch command, not that it stayed there). `swarm_node` now confirms the *actual* flight mode via `Telemetry::subscribe_flight_mode` and retries (up to 5x) rather than trusting a single `start()` call — this was happening on close to every takeoff once looked for, not a rare fluke, so the retry isn't optional polish.
- **`test_formation.py` now actually passes both its tests — it never had before.** `drone_0.terminate()` in the failover test was never valid (`launch_ros.actions.Node` has no such method) and had sat unexercised since the file was first written, since leader failover had only ever been verified by hand. Fixed by killing the process directly (`pkill -f __node:=drone_0`, matching the manual verification method used throughout this project) instead. Confirmed a real, `OK` end-to-end pass. Still requires PX4 SITL already running by hand (`HEADLESS=1 ./run_swarm.sh` — booting Gazebo + 3 PX4 instances from inside a test is too slow/flaky for `colcon test`), so it isn't wired into CI-style automatic runs. A fully self-contained version (this test launching `run_swarm.sh` itself) was attempted and reverted after surfacing two more real, fixed-and-kept bugs along the way — a `launch.actions.TimerAction` delaying node startup silently breaking `launch_testing`'s fixture injection, and `run_swarm.sh`'s PX4 stagger (now 15s → 25s) not being enough under the extra concurrent load — but a third, unexplained stall meant the fully-automated version wasn't reliable enough to ship; see `test_formation.py`'s own header comment for the full story.
- **RoboStack (native ROS 2 on macOS) vs. the Docker `ros:jazzy` container**: flight requires native ROS 2 so it can reach PX4/MAVSDK/Gazebo over localhost — the Docker workflow from earlier in the project still works for comm/election-only testing but not for real flight.

##  Files

- `launch_all.sh` — builds if needed and opens all 4 terminal windows automatically (the fastest way to run everything for the original non-ROS prototype).
- `run_swarm.sh` — starts the 3 PX4 SITL instances in the persistent world. Still the entry point for flight — used by both the old prototype and `ros2_ws`. Run as `HEADLESS=1 ./run_swarm.sh` for any automated testing or measurement (skips Gazebo's GUI client, which otherwise competes with the 3 physics instances for CPU/GPU and measurably worsens connectivity jitter — see "What's left"); leave it unset for interactive demos where you want to watch it fly.
- `swarm_node.cpp` / `CMakeLists.txt` — the original UDP-mesh prototype (`./build/swarm_node --id 0|1|2`), comm/election only, no flight.
- `worlds/swarm_persistent.sdf` — the Gazebo world with the 3 drones already placed in it.
- `ros2_ws/src/swarm_comm/src/swarm_node.cpp` — the active implementation: comm, election, MAVSDK flight, formation, collision avoidance.
- `ros2_ws/src/swarm_comm/launch/swarm_launch.py` — `ros2 launch swarm_comm swarm_launch.py`, starts all 3 drones.
- `ros2_ws/src/swarm_comm/test/test_election.py` — comm/election regression tests, no PX4 required, runs under `colcon test`.
- `ros2_ws/src/swarm_comm/test/test_formation.py` — flight/formation/failover tests, requires `run_swarm.sh` already running, run by hand (see the file header).
- `ros2_ws/tools/swarm_dashboard.py` — live terminal dashboard: position, leader, distance to leader, min pairwise separation (flagged red under 1m).

##  Requirements

- PX4-Autopilot built for `gz-sim` (`make px4_sitl`).
- MAVSDK C++ (`brew install mavsdk` on macOS).
- CMake ≥ 3.16 and a C++17 compiler.
- ROS 2 Jazzy, native on macOS via [RoboStack](https://robostack.github.io/) (`micromamba create -n ros_env -c robostack-jazzy -c conda-forge ros-jazzy-ros-base colcon-common-extensions compilers cmake`) — needed for `ros2_ws`, since real flight requires ROS 2 and MAVSDK/PX4/Gazebo to share a network namespace, which the Docker `ros:jazzy` container can't do on Docker Desktop for Mac.
- `export ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST` before running anything in `ros2_ws` — without it, DDS multicast discovery on macOS can take 5+ seconds (vs. <1s with it set), which is slow enough to make the election's outcome timing-dependent.
